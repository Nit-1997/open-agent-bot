# Security: hosted service

Report vulnerabilities as described in the repository's [SECURITY.md](../SECURITY.md), which also covers supported versions, verifying a download, the local stack and the Mac app. This file holds the hosted deployment's threat model.

## Hosted service

The invite-only hosted deployment (setup in [README.md](README.md)).

### Threat model

Open Agent runs for a small invited group: the web app on Vercel, the agent behind Caddy on one server, and every user's data in one Supabase project.

- **Invite-only accounts.** Supabase sign-ups are off (`disable_signup`), and a `before-user-created` Postgres hook only lets in emails an admin approved (`public.invited_emails`). The admin API's `createUser` does not run that hook, so only the owner's admin scripts call it.
- **Sessions.** The web app holds the Supabase session in `HttpOnly; Secure; SameSite=Lax` host-only cookies through `@supabase/ssr` server clients. The browser has no Supabase client and no readable token.
- **Web to agent.** Server to server only, with the user's access token and the service secret (`AGENT_SERVICE_SECRET`). The agent verifies the token against the project's ES256 JWKS and takes the user id only from it, checks the account is active on every request, and re-checks the admin role live for admin routes. Browser headers are never forwarded.
- **Data isolation.** Postgres RLS is on with no policies or grants for `anon` or `authenticated`, so the publishable key reads nothing. Only the agent's secret key touches data, through repositories that put the verified user id into every query and Storage path. Integration tests (`npm run test:supabase -w @oab/cloud-agent`) prove the denial for every table, function and the artifacts bucket.
- **Keys at rest.** Provider keys and OAuth tokens are sealed with AES-256-GCM under a per-row data key wrapped by a master key from `CREDENTIAL_KEYS`, bound to the user, provider and kind. The browser only ever sees a hint like `sk-ant-…a91f`. Logs mask keys and tokens.
- **Model-controlled network access.** Pages the agent reads can contain prompt injection. `fetch_page` refuses private, loopback and link-local addresses, including public names that resolve to them, on every request and redirect (`packages/core/src/lib/net.ts`). The agent's Chromium applies the same check to every request a page makes, scripts and images included (`packages/core/src/browser/guard.ts`), and refuses login, cart, checkout and booking steps (`packages/core/src/browser/policy.ts`). Custom model servers must be public addresses for everyone but the admin. The DNS check runs just before each request, so a hostname whose DNS answer changes in the gap between the check and the request is still a residual risk.
- **Artifacts.** Model-written HTML lives in a private Storage bucket, is served only through the agent and web with `Content-Security-Policy: sandbox allow-scripts` and `nosniff`, and is shown in a sandboxed iframe, so it can't reach the app's origin.
- **Chat stream proxy.** The browser reaches the CopilotKit runtime only through `/api/copilotkit/*`, which `@oab/bff` forwards to the agent's `/copilotkit` for an allowlist of four endpoints (`GET info`, `POST agent/openagent/run`, `agent/openagent/connect`, `agent/openagent/stop/<thread>`), drops the query, copies only `content-type` back and sets `private, no-store`; everything else answers 404 or 405. Unsafe methods need a same-origin `Origin`. In the agent, a stop, connect or run on another user's thread answers 403 `forbidden`; runs are scoped per user, so isolation never depends on the owner map. Each user may hold at most `COPILOT_CONNECTS_PER_USER` connect streams (429 over the cap), each bounded by `COPILOT_CONNECT_MAX_MS`. Bodies are capped before they are read: 4 MiB for a run, 1 MiB for everything else, chunked bodies included. CopilotKit telemetry is forced off: the agent refuses to start unless `COPILOTKIT_TELEMETRY_DISABLED=true`.
- **Request limits.** Every run goes through one admission check before it starts: per-user and server-wide running caps held in the agent process (slots keyed by a ticket the agent mints, released when the run has really ended, and force-released after `RUN_TIME_LIMIT_SECONDS` + 60 s), then an hourly and a monthly per-user count in Postgres (`request_admit`, serialized per user by an advisory lock, callable by `service_role` only). An in-memory attempt limiter (60 per 10 minutes) and a cache of monthly/hourly refusals stop retry storms before they reach the database. The checks fail closed: a database error or a 3 s timeout answers 503 `usage_unavailable` and never admits an uncounted run, and the agent refuses to start while the functions are missing. The same limits apply to every account, admins included. The hourly cap replaces the hosted agent's old burst limit of 30 runs per 10 minutes. A run that the agent refuses before it starts (session capacity, a busy thread, a duplicate run id, or a stop before it began) is refunded; a run that times out after the count committed stays counted.
- **Admin capabilities.** Admin routes, private-network model servers and the operator's model gateway need both the `role` claim in the access token and a live admin check through the Auth admin API (cached 30 s per user; a banned account fails it). A member's token never triggers the lookup. A demoted admin loses private-network models and the operator gateway within 30 s, including in existing chats; in-flight runs are aborted. Any change from admin to member (a refreshed token without the claim, or the live check saying no) drops the user's chat sessions. If the live lookup fails, that request is served without admin capabilities, admin routes answer 503, and a chat session built with them is rebuilt without them.
- **Signups.** The mode lives in one row of `public.signup_settings` and changes only through the owner's `configure-auth.mjs`. In `invite` and `waitlist` the `before-user-created` hook keeps today's invite-only rule. In `open` it admits only a Google sign-up whose email domain (or a parent domain) isn't on the vendored throwaway list, within global hourly and daily caps and a per-IP daily cap; every other way to create an account (email link, password, phone) is refused. The hook logs an allowed signup only after every check passed. If the agent can't read the mode it treats it as `open` for the human check, and the web app shows `waitlist`, so neither fails open.
- **Human check.** In `open` mode every account, invited ones included, passes one Cloudflare Turnstile check before its first counted run, and the email-link form needs one too. The agent verifies each token with Cloudflare (success, the app's hostname and the expected action), keyed by the session user id only, rate-limited 10 per 10 minutes; Cloudflare unreachable fails closed. Cloudflare's public test keys are refused outside the local test stack, and tokens and secrets are never logged.
- **Account deletion.** A member can delete their own account by typing its email (3 tries per hour; an admin can't delete themselves this way). The agent first drops the user's sessions and aborts their runs, refuses new runs for that id, then deletes their files, access requests and the auth account with everything that belongs to it. It keeps a peppered SHA-256 of the email with that month's request count and the human check for up to two months, so deleting and signing up again with the same email doesn't reset either.
- **Agent host.** The agent container runs read-only with tmpfs scratch space, no capabilities and no volumes; nothing user-owned is written to its disk.

### Accepted risks

The owner accepts these when signups open (Gate 9 in [README.md](README.md)):

- **The browser tool's egress.** With open signups anyone with an account can drive the agent's browser tool, and its requests leave from the owner's network and IP address. The private-network guard stays on for everyone but the admin, and login, cart, checkout and booking steps stay refused.
- **Global signup caps.** An attacker can fill the hourly or daily signup cap and pause signups for real users until the window passes. The admin Usage tab shows the counts, and the emergency close goes back to `waitlist`.
- **Bots through Google.** Bots can drive Google's sign-in flow directly, past the web app. The hook's caps, the throwaway list, the human check before the first run and the cost of Google accounts bound it.
- **Per-IP cap.** The per-IP signup cap is best effort: it uses the address GoTrue reports, which a client may be able to set; the global caps are the real bound.
- **A request that times out after it was counted** stays counted, at most one per occurrence.
- **A new email gets a new quota.** The delete carry-over follows the same email only; the signup caps and the throwaway list bound the rest.
